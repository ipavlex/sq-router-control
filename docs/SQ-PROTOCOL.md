# Протокол SQ — справочник

> Документация по бинарному протоколу Allen & Heath SQ (SQ-5 / SQ-6 / SQ-7),
> восстановленному реверс-инжинирингом в проекте SQ Router Control.
> Проверено на SQ-5, FW 1.6.4812. Публичных спецификаций от A&H нет —
> всё снято с реального трафика (MixPad) и подтверждено на живом пульте.

## Обзор

Пульт SQ общается по **двум транспортам**:

| Транспорт | Порт | Назначение |
|---|---|---|
| TCP | `51326` | управление: хендшейк, подписка, DSP-кадры, дампы состояния |
| UDP | согласуется при хендшейке | поток метров (уровни сигнала) |

Все многобайтовые целые — **little-endian**. Строки — ASCII, null-terminated.

## 1. Кадрирование TCP

### 1.1. Фрейм с заголовком (маркер `0x7F`)

```
[0x7F] [subType:u8] [length:u32LE] [payload × length]
```

Заголовок — 6 байт: маркер (1) + подтип (1) + длина (4).

### 1.2. DSP-кадр (маркер `0xF7`, фиксированные 8 байт)

```
[0xF7] [ch:u8] [category:u8] [register:u8] [modifier:u8] [value:u16LE] [pad:u8]
```

`0xF7` + 7 байт полезной нагрузки. Поля payload:
`payload[1]` = category, `payload[2]` = register, `payload[3]` = ch (b3),
`payload[4]` = modifier, `value` = u16LE на офсете 5.

DSP-кадры перемежаются с фреймами `0x7F` в одном TCP-потоке. Фреймер
(`Framer` в `src/main/transport/frame.ts`) различает их по первому байту;
при потере синхронизации сбрасывает байты до следующего маркера.

### 1.3. Подтипы фреймов

| subType | Имя | Направление | Назначение |
|---|---|---|---|
| `0x00` | MeterSub | app ↔ mixer | обмен UDP-портами метров |
| `0x01` | Ack | app → mixer | пустой ack после `0x00` |
| `0x02` | Version | mixer → app | модель и версия прошивки |
| `0x03` | Keepalive | app → mixer | пустой, каждые ~1000 мс |
| `0x04` | ParamData | mixer → app | большой дамп параметров (~97 КБ) |
| `0x08` | ChannelInfo | mixer → app | имена каналов, список сцен |
| `0x0A` | Subscribe | app → mixer | подписка на все параметры (8192 Б `0xFF`) |
| `0x0B` | TypeReq | app → mixer | payload `[02 00]` — согласование типа |
| `0x0C` | TypeResp | mixer → app | payload `[01 00]` |
| `0x0D` | SubExtra1 | app → mixer | пустой, после подписки |
| `0x0E` | FullState | mixer → app | таблица каналов/параметров (8200 Б) |
| `0x0F` | SubExtra3 | app → mixer | пустой |
| `0x10` | Block16 | mixer → app | routing/config блок (928 Б) |
| `0x11` | SubExtra2 | app → mixer | пустой |
| `0x12` | Block18 | mixer → app | блок 32 Б |
| `0x14` | StateAck | app → mixer | пустой, после `0x15` |
| `0x15` | InitState | mixer → app | начальное состояние (720 Б) |
| `0x19` | Sync | mixer → app | пустой, конец начального шторма |

## 2. Хендшейк

Последовательность (восстановлена по трафику SQ MixPad):

| Шаг | Направление | Кадр | Смысл |
|---|---|---|---|
| 1 | app → mixer | `[sub=0x00, len=2, payload=udpPort_LE16]` | «шлю метры на этот UDP-порт» |
| 2 | mixer → app | `[sub=0x00, len=2, payload=mixerPort_LE16]` | порт-источник метров пульта |
| 3 | app → mixer | `[sub=0x01, len=0]` | ack |
| 4 | mixer → app | `[sub=0x02, len≥4, payload=version]` | модель / прошивка |
| 5 | app → mixer | `[sub=0x14, len=0]` | state-ack |
| 6 | mixer → app | `[sub=0x15, len=720]` | начальный блок состояния |
| 7 | app → mixer | `[sub=0x0B, len=2, payload=[02 00]]` | согласование типа |
| 8 | mixer → app | `[sub=0x0C, len=2, payload=[01 00]]` | ответ типа |
| 9 | app → mixer | `[sub=0x0A, len=8192, payload=все 0xFF]` | подписка на все параметры |
| 10 | app → mixer | `[sub=0x0D / 0x11 / 0x0F, len=0]` | доп. подписки |
| 11 | mixer → app | шторм данных (`0x04`, `0x08`, `0x0E`, `0x10`…) | дампы состояния |
| 12 | app → mixer | `[sub=0x03]` каждые ~1000 мс | keepalive |

После шага 10 приложение также отправляет триггер списка сцен
`F7 02 02 20 FF FF FF FF` (через ~160 мс) — повторяет поведение MixPad.

### 2.1. Кадр Version (sub=0x02)

```
[model:u8] [fwA:u8] [fwB:u8] [?] [build:u16LE]
```

| model | Пульт |
|---|---|
| `0x01` | SQ-5 |
| `0x02` | SQ-6 |
| `0x03` | SQ-7 |

### 2.2. Повторный запрос полного дампа

Повторная отправка последовательности шагов 9–10 (`Subscribe` + SubExtra1–3 +
триггер сцен) заставляет пульт заново вылить всё состояние. Это единственный
проверенный механизм запроса роутинга по требованию.

## 3. DSP-кадры: карта регистров

Формат: `F7 [x] cat reg [b3] mod valLo valHi`. Параметры каналов:

| cat | reg | mod | Параметр | Кодировка |
|---|---|---|---|---|
| `0x07` | `0x0c` | — | мьют | 1 = muted, 0 = unmuted |
| `0x07` | `0x0e` | `0x20` | фейдер | база `0x8000`, 256/дБ (0 = −∞) |
| `0x07` | `0x0e` | `0x10`–`0x1b` | сенд на шину 1–12 | 0..35328 (0 дБ = максимум) |
| `0x07` | `0x0e` | `0x23`–`0x26` | сенд на FX 1–4 | 0..35328 |
| `0x07` | `0x10` | `0x20` | панорама | байт 0..74, 37 ≈ центр |
| `0x0c` | `0x0c` | — | входной гейн | база `0x8000`, 256/дБ (0..+60 дБ) |
| `0x0c` | `0x0f` | — | трим | 26624 = −24 дБ … 36824 = +24 дБ (212.5/дБ) |
| `0x0c` | `0x10` | — | полярность | 1 = инвертирована |
| `0x0e` | `0x0c` | — | HPF вкл/выкл | 0/1 |
| `0x0e` | `0x0d` | — | частота HPF | wire = −9206 + 15308·log₁₀(Гц) |
| `0x0f` | `0x0c` | — | гейт вкл/выкл | 0/1 |
| `0x13` | `0x0c` | — | компрессор вкл/выкл | 0/1 |
| `0x14` | `0x0c` | — | делэй вкл/выкл | 0/1 |
| `0x14` | `0x0d` | — | длительность делэя | 96 ед/мс (0..341 мс) |

## 4. Патчинг (category `0x0b`, register `0x0d`)

Все патч-кадры имеют вид:

```
F7 0B 0B 0D [ch] [modifier] [valLo] [valHi]
```

Декодируются по байту `modifier`:

| modifier | Тип патча | Поля |
|---|---|---|
| `0x01`–`0x04` | **Input patch** (физ. источник → канал микшера) | `ch` = канал источника, `valLo` = destB3, `valHi` = `0x20` |
| `0x0F` | **Output patch** (шина/канал → физ. выход) | `ch` = sourceB3, `valLo` = destChannel−1, `valHi` = destType |
| `0x16` / `0x17` | **FX return output patch** (L / R) | `ch` = fxIndex (0-based), `valLo` = destChannel−1, `valHi` = destType |
| `0x11` | **Monitor output patch** | `ch` = источник монитора, `valLo` = destChannel−1, `valHi` = destType |

### 4.1. Коды источников инпатчинга

| Код | Источник |
|---|---|
| `0x01` | Local |
| `0x02` | SLink (dSk / dSnake) |
| `0x03` | USB |
| `0x04` | I/O Port |

### 4.2. Коды назначений аутпатчинга

| Код | Назначение |
|---|---|
| `0x1A` | Local Out |
| `0x1B` | ME (Mon) |
| `0x1C` | SLink (dSnake) |
| `0x1D` | USB |
| `0x1E` | I/O Port |

### 4.3. Источники мониторного выхода

| Код | Источник |
|---|---|
| `0x00` | PAFL L |
| `0x01` | PAFL R |
| `0x02` | Listen L |
| `0x03` | Listen R |
| `0x04` | Listen M |
| `0x05` | Talkback |

### 4.4. Инварианты

- **Один источник на физическом выходе**: новый патч вытесняет предыдущий
  источник того же `(dest, destChannel)`. Один источник может легитимно
  идти на несколько выходов (моно → L и R).
- **Стерео-линкованная пара** роутится одним кадром левого (мастер-) канала —
  правую половину пульт сам заводит на соседний сокет (правило чётных/нечётных
  пар). Пульт игнорирует output-patch кадр с правым (ведомым) каналом пары.
- Пульт **не возвращает эхо** отправленных приложением input-патчей в потоке
  подписки — приложение применяет их к локальной модели оптимистически.

### 4.5. Прочие управляющие DSP-кадры

| Назначение | Кадр |
|---|---|
| PAFL (соло) шины/Main LR | `F7 08 15 0C [b3] 00 [valLo] [valHi]`, val = `0x0001`/`0x0000` |
| Подтверждение реколла сцены | `F7 02 02 1C [sceneId] 00 FF FF` (sceneId 0-based) |
| Триггер дампа списка сцен | `F7 02 02 20 FF FF FF FF` |

## 6. Дамп ParamData (sub=0x04, ~97 КБ)

Начальное состояние микшера приходит сразу после подписки. Приложение
разбирает его целиком, поэтому состояние каналов известно сразу, не дожидаясь
живых изменений. Карта смещений подтверждена на SQ-5 FW 1.6 (эталон —
[allen-heath-sq-tools](https://github.com/hrueger/allen-heath-sq-tools)).

### 6.1. Блок канала (336 Б) на офсете `884 + b3·336`

| Офсет | Поле |
|---|---|
| `+0..15` | имя канала (16 Б, ASCII, null-padded) |
| `+24` / `+26` | инпатчинг: канал источника / тип источника (b3 ≤ 0x2F) |
| `+84,85` | частота HPF (u16LE) |
| `+87` | HPF вкл/выкл |
| `+121` | гейт вкл/выкл |
| `+302` | компрессор вкл/выкл |
| `+304,305` | длительность делэя (u16LE) |
| `+306` | делэй вкл/выкл |
| `+324,325` | трим (u16LE) |
| `+332` | флаги: bit0 = полярность, bit1 = мьют |

### 6.2. Секция фейдеров/сендов (300 Б) на офсете `43520 + b3·300`

| Офсет | Поле |
|---|---|
| `+0..67` | сенды на шины 1–12 (шаг 6) |
| `+96,97` | фейдер (u16LE) |
| `+98` | панорама (байт) |
| `+114..133` | сенды на FX 1–4 (шаг 6) |

### 6.3. Гейн преампа

Абсолютный офсет `80028 + b3·336` (u16LE; помещается только для b3 ≤ 0x32).

### 6.4. Таблица стерео-линков

Офсет `81548`, 4 байта на запись: `[target:u16LE] [flags:u8] [0xFE tail]`.
Декодируются только 48 входных каналов (b3 0x00–0x2F). Две кодировки:

**Кодировка A** (классическая, Ch1–32):
- моно: flags `0x0F`, target = собственный b3;
- пара: левый flags `0x0F`, target = собственный b3; правый flags `0x10`,
  target = b3 левого партнёра.

**Кодировка B** (слот-пара, Ch33+):
- обе стороны flags `0x0F`, левый target = X, правый target = X+1,
  где X ≠ собственный b3 и X ≠ 0.

> **Ловушка**: таблица продолжается за входными записями (FX-возвраты,
> мастера), и slot-id кодировки B там численно совпадают с b3 миксов
> (0x58–0x63). Записи входов 44–47 (Ch45–48) несут такие target-ы — их легко
> принять за self-target миксов и «урезать» скан. Сканируются ровно 48 входных
> записей и ничего дальше.

## 7. Список сцен (sub=0x08, ChannelInfo)

**Формат списка**: заголовок `[02 02 xx 00 00 00 00]`, затем записи по 18 Б:
`[flag] [имя до 16 Б, null-padded] [pad]`. Известные флаги: `0x07` = сохранённая
сцена, `0x00` = пустой слот.

**Записи полного состояния** (после реколла/переименования/сохранения):
`00 02 18 [sceneId] 40 00 00 [имя 16 Б]`.

**Активная сцена**: в бинарном протоколе SQ **нет запроса** активной сцены.
Единственный источник правды — живой кадр подтверждения реколла
`F7 02 02 1C [sceneId] 00 FF FF`, который пульт шлёт после каждого реколла
(с поверхности, софт-кейсов, MIDI). До первого реколла активная сцена
неизвестна.

## 8. UDP-метры

### 8.1. Формат дейтаграммы

```
[0x7F] [id:u8] [len:u16LE] [00 00] [body × len]
```

Тело — массив u16 LE. UDP-порт источника пульт сообщает в ответе на
MeterSub (sub=0x00) при хендшейке.

### 8.2. Кодировка уровней (общая для всех пакетов)

| Значение | Смысл |
|---|---|
| дБФС = `(raw − 0x8000) / 256` | уровень; `0x8000` = 0.00 дБФС |
| `0x1201` | пол — «нет сигнала» (≈ −286 дБ) |
| `raw > 0x8000` | клип (> 0 дБФС) |
| `0x0000`, `≥ 0xF000` | заглушки-данные, уровнем не считать |

### 8.3. Известные id

| id | Тело | Содержимое | Статус |
|---|---|---|---|
| `0x05` | 0 Б | keepalive (аналог `0x25` у Qu) | — |
| `0x06` | 1056 Б | 48 входов × 11 слотов. Ровно 1056 Б — хвоста нет | **декодируется** |
| `0x07` | 1416 Б | 6 заголовка + 78 записей × 9 слотов (18 Б); те же шины по 2 записи, у нечётных офсет ~+0.1 дБ (пик-латч?) | не декодирован |
| `0x09` | 100 Б | 50 значений; за весь захват висел на полу — миксов не содержит | не декодирован |
| `0x16` | 1168 Б | те же шины/слоты, что 0x18, но на ~10 дБ тише (пре-фейдерные тапы) + хвост с параметр-данными | не декодирован |
| `0x17` | 96 Б | 48 входов, по одному уровню | **декодируется** |
| `0x18` | 480 Б | 40 шин × 6 слотов — Main LR, Mix 1–12, FX send | **декодируется** |

### 8.4. Раскладка пакета 0x18 (40 шин × 6 u16)

| Шины | Слоты | Содержимое |
|---|---|---|
| 0–22 | 0–137 | входные каналы 1–23 (здесь не используются — входы уже в 0x06/0x17) |
| **23** | **138–143** | **Main LR** |
| **24–35** | **144–215** | **Mix 1–12** (шина = 23 + номер микса) |
| 36–39 | 216–239 | FX send 1–4 |

Внутри 6-слотного блока шины — **две L/R-пары тапов**: `[s0, s1]` и `[s3, s4]`
(слот `s2` = `0x0000`, `s5` = `≥0xF000` — заглушки). Пары — два измерительных
тапа одной шины (значения близки, но не равны); по стороне берётся максимум.

Наблюдения с живого пульта (SQ-5, обычная программа):
- стерео-линкованная шина метрирует пары бит-в-бит идентично (пары 75/76
  всегда равны);
- пары 69–71, 78, 108–110, 117–119 постоянно горячие (~−2…−8 дБ, медленно
  «дышат») — похоже на FX-возвраты / DCA / мониторные выходы с программой.

### 8.5. Стерео-режим миксов

На SQ миксы не «линкуются» как каналы — у шины есть режим стерео/моно
(стерео-микс занимает один слот Metering, шины не сдвигаются):

- **стерео-микс**: s0 ≠ s1 (L ≠ R); шина-партнёр — на полу;
- **моно-микс**: s0 == s1 бит-в-бит, вторая пара на полу;
- **Main LR**: всегда L ≠ R.

Стерео определяется двумя путями: из снапшота (`mixStereoPairs`, декодер
таблицы линков в ParamData) или поведенчески — защёлка при расхождении L/R
≥ 0.4 дБ (моно даёт бит-равные стороны, ложных срабатываний нет).

> Открытый вопрос: где в ParamData лежит бит режима стерео/моно миксов.
> Таблица линков (входная часть) режим не отражает.

### 8.6. Диагностика метро-потока

Для недекодированных форм приложение ведёт инвентаризацию: каждый уникальный
формат (id + длина тела) логируется один раз, недекодированные ре-сэмплятся
раз в 4 секунды с dB-снимком, картой изменений (`chg:`) и списком самых
горячих слотов (`hot:`). Сырые дейтаграммы сохраняются в
`<userData>/diagnostics/meter-packet-0x<id>-<len>B.bin` — один файл на форму
пакета за сессию.

Формат строки лога:

```
Meter packet: id=0x07 body=1416B (undecoded) dB: [0]-inf … [8]0.1 … hot: [8]-2.3 [23]-3.1 chg: [8]-14.2 [23]-3.1
```

- `dB:` — снимок слотов тела (первые 16 для больших тел, целиком для ≤ 64 значений);
- `hot:` — топ-6 самых горячих слотов (≥ −54 дБ), по уровню; при изолированной
  подаче сигнала верхний слот прямо называет шину;
- `chg:` — карта изменений: слоты, сдвинувшиеся с прошлого снимка (≥ ~0.25 дБ),
  до 12 штук;
- «тихий режим»: строка пишется только при первом появлении формы или когда
  слоты реально сдвинулись — steady-state снимки не засоряют лог.

### 8.7. Решения реализации (декодер метров)

1. **Реверс через изолированные захваты**, а не спекулятивный декодер —
   формат нигде не опубликован; инструменты сбора (метки, тихий режим, дампы)
   сделали финальный захват однозначным.
2. **Максимум из 4 уровневых слотов** на шину — пары L/R близки, max надёжен
   для бара.
3. **Отдельное состояние `busMeters` + мерж в каждый payload** — миксы не
   «мигают» между редкими 0x18-пакетами (пульт шлёт их заметно реже входных).
4. **Тихий режим лога** — строка только при первом появлении формы или сдвиге
   слотов ≥ 0.25 дБ; без этого лог утопал в повторах.
5. **Диагностику оставить** — дампы/снимки дёшевы и нужны для 0x07/0x16
   в будущем.

### 8.8. Ловушка для тестов

6-байтовый заголовок UDP-пакета = 3 u16-слота: запись в слот 0 «тела» затирает
`msg[0]/msg[1]`. Тестовые сообщения собирать только через
`Buffer.concat([header, body])`.

## 9. Модели пультов

Все SQ разделяют один DSP-движок на 48 входов, но различаются физическим I/O:

| | SQ-5 (`0x01`) | SQ-6 (`0x02`) | SQ-7 (`0x03`) |
|---|---|---|---|
| XLR-входы | 16 | 24 | 32 |
| Линейные входы (ST1–ST3) | 6 | 6 | 6 |
| Локальных входов всего | 22 | 30 | 38 |
| XLR-выходы | 12 | 14 | 16 |
| TRS-выходы (A/B) | 2 | 2 | 2 |
| Локальных выходов всего | 14 | 16 | 18 |
| USB-аудио | 32×32 | 32×32 | 32×32 |
| Миксы | 12 | 12 | 12 |
| DCA | 8 | 8 | 8 |

ST1–ST3 привязаны к фиксированным проводным каналам 49–54 (0-based 48–53)
банка Local на любой модели. Талбэк-микрофон — проводной канал 59.

## 10. Известные неизвестные

### 10.1. Недекодированные метро-пакеты

**Пакет 0x07** (1416 Б = 708 u16). Раскладка по изолированному захвату:
708 = 6 заголовка + 78 записей × 9 слотов (18 Б). У записей offset 2 —
константа ~+0.1 дБ (пик-латч?), offsets 4–8 — уровни группами {4,5,6} равны
и {7,8} равны. 78 записей похоже на «48 инпутов + 12 миксов + 14 local outs
+ LR + 3 ST». Те же шины по 2 записи на шину (Mix 1 = записи 0–1, LR = 16,
FX = 12–15 …). Редкие всплески до ~0 дБ (слоты 37–44), константный 0.1 дБ
на слоте 8.

**Пакет 0x16** (1168 Б = 584 u16). Зеркалит индексы 0x18 (те же шины на тех
же слотах), но на ~10 дБ тише — пре-фейдерные тапы. В хвосте (слоты 529+)
статичные +17…+18 — параметр-данные, не уровни. Сентинел `0xFFFF`
(= «128.0 дБ») на слотах 351/384/367/400 — данные, в `hot:` отфильтровываются.

**Пакет 0x09** (100 Б = 50 значений). За весь захват висел на полу — миксов
не содержит (или в миксы не шло сигнала).

### 10.2. Открытые вопросы

- **Бит режима стерео/моно миксов** в ParamData не найден. Таблица линков
  (входная часть, офсет 81548) режим не отражает; расширение таблицы за
  входами (FX-возвраты, мастера) не декодируется. Сейчас стерео определяется
  поведенчески (защёлка при расхождении L/R ≥ 0.4 дБ).
- **Активная сцена** не запрашивается — только наблюдается через кадры реколла.
- **id метро-пакетов не переносятся между моделями** семейства A&H — при
  работе с другой моделью раскладку нужно проверять заново. Семейный паттерн:
  один пакет инпутов + один пакет аутпутов (аутпут несёт миксы, группы и
  Main L/R вместе), значения — те же u16 dBFS с floor-сентинелом:
  - Qu: `0x23` инпуты (32×20 Б, уровень @+6), `0x24` аутпуты (миксы @0,
    Main L @200, Main R @220, уровень @+10 в 20-байтной записи);
  - CQ: `0x08` инпуты, `0x09` аутпуты (16 Б шаг, уровень @+14, idx 6/7 =
    Main L/R).
