## РЕШЕНО: формат живых метро-пакетов (2026-09-10)

Раскладка восстановлена по трём изолированным захватам с метками (Mix 1 → Mix 5 →
Mix 12 → LR) + сырым дампом. Ключевой пакет — **id=0x18, тело 480 байт = 40 шин × 6 u16**:

| Шины | Слоты | Содержимое |
|---|---|---|
| 0–22 | 0–137 | входные каналы b3 0–22 (здесь не декодируются — входы уже в 0x06/0x17) |
| **23** | **138–143** | **Main LR** |
| **24–35** | **144–215** | **Mix 1–12** (шина 23 + номер микса) |
| 36–39 | 216–239 | FX send 1–4 |

- Уровневые слоты внутри 6-слотного блока шины: **+0, +1 и +4, +5** (две L/R-пары,
  значения близкие; в декодере берётся максимум); слот +2 = 0x0000, +3 = 0xFFFF (заглушки).
- Кодировка общая с входными пакетами: дБФС = (raw − 0x8000)/256, пол 0x1201,
  клип = raw > 0x8000.
- Реализация: `decodeBusLevel` + ветка `id=0x18` в `src/main/meters.ts`; состояние
  шин хранится отдельно и мержится в каждый `MetersPayload` (`mergeMeters`), чтобы
  миксы текли в рендерер непрерывно между 0x18-пакетами. `resetMeters()` чистит.
- UI изменений не потребовал — бары на кнопках Mix/Main LR уже читали
  `mixes`/`mainLR` (демо-ветка). Метки «demo mode only» в типах убраны.

Дополнительные находки (не декодированы, пригодятся если понадобится):
- `0x07` (1416B = 6 заголовка + 39 шин × 18 слотов): те же шины, по 2 записи на шину
  (Mix 1 = записи 0–1, LR = 16, FX = 12–15 …); офсет-константа ~+0.1 на каждой нечётной
  записи (пик-латч?).
- `0x16` (1168B): те же шины на тех же слотах, что 0x18, но тише на ~10 дБ
  (пре-фейдерные тапы) + хвост с параметр-данными (сентинелы 0xFFFF, константы +17…+18).
- `0x09` (50 значений) и `0x05` (0B, keepalive) — миксов не содержат.

## История блокера (для археологии)

Публичных данных нет — даже hrueger/allen-heath-sq-tools помечает Metering как «UDP Only, format TBD».
Наш декодер входных каналов (`src/main/meters.ts`) знает только:
- `id=0x06` — 48 каналов × 11 слотов (тело 1056 байт);
- `id=0x17` — 48 значений (тело 96 байт).

### Результаты поиска по открытым источникам (2026-09-10)

- **Прямого ответа нет нигде**: hrueger/allen-heath-sq-tools отдаёт UDP-метры сырыми
  (`meterData`, «format TBD»); у jskeet/DemoCode (DigiMixer) поддержка SQ — заглушка.
- Родственные консоли используют **тот же транспорт** (TCP 51326 + UDP с той же
  кадровой структурой и кодировкой dBFS), но **id пакетов не переносятся между моделями**:
  - Qu: `0x23` инпуты (32×20Б, уровень @+6), `0x24` аутпуты (миксы @0, Main L @200,
    Main R @220, уровень @+10 в 20-байтной записи);
  - CQ: `0x08` инпуты, `0x09` аутпуты (16Б шаг, уровень @+14, idx 6/7 = Main L/R).
- Семейный паттерн: **один пакет инпутов + один пакет аутпутов**, аутпут-пакет несёт
  миксы, группы и Main L/R вместе; значения — те же u16 dBFS с floor-сентинелом.
- Кандидаты для SQ (пары к известным 0x06/0x17): **0x07, 0x18, 0x19**; плюс гипотеза
  хвоста пакета 0x06 (декодер требует ≥1056Б, реальный может быть длиннее).

### Гипотезы для проверки на реальном пульте

1. **Хвост пакета 0x06**: декодер требует `body.length >= 1056`, но реальный пакет может быть длиннее — уровни миксов/LR/FX могут лежать в слотах 48+ или в хвосте. Проверка: смотрим фактическую длину тела 0x06 в логе инвентаризации.
2. **Отдельный пакет с другим id** (0x07 / 0x18 / 0x19 по семейному паттерну): тело на 12–14+ значений (Mix 1–12, Main LR, матрицы, FX). Проверка: строки `Meter packet: id=0x.. body=..B (undecoded)` в логе.
3. **Кодировка та же**, что у входов: u16 LE, dBFS = (value − 0x8000)/256, floor ≈ 0x1201 (проверить на живых данных).

### Диагностика в приложении (улучшено 2026-09-10)

Каждый уникальный формат UDP-пакета логируется строкой вида:

```
Meter packet: id=0x07 body=1416B (undecoded) dB: [0]-inf … [8]0.1 … chg: [8]-14.2 [23]-3.1
```

- `dB:` — снимок слотов тела (первые 16 для больших тел, целиком для ≤ 64 значений);
- `chg:` — **карта изменений**: слоты, сдвинувшиеся с прошлого снимка (≥ ~0.25 дБ),
  до 12 штук;
- недекодированные форматы сэмплятся **раз в 4 секунды**; декодированные — один раз.

Реализация: `meterSamplePreview` / `meterBody` / `diffMeterBody` / `formatMeterChanges`
в `src/main/meters.ts`, `_noteMeterPacket` + `_meterPrev` в
`src/main/transport/connection.ts`, обработчик `meterPacketInfo` в `src/main/main.ts`.

### Инвентарь, снятый с реального пульта (2026-09-10, SQ-5)

| id | тело | u16 | статус / примечание |
|---|---|---|---|
| `0x05` | 0B | — | keepalive (аналог `0x25` у Qu) |
| `0x06` | 1056B | 528 | **декодирован**: 48 инпутов × 11 слотов. Ровно 1056B — хвоста нет, гипотеза «миксы в хвосте 0x06» опровергнута |
| `0x07` | 1416B | 708 | недекодирован; 708 = 4 + 64×11; редкие всплески до ~0 дБ (слоты 37–44), константный 0.1 дБ на слоте 8 |
| `0x09` | 100B | 50 | недекодирован; за весь захват висел на полу — не миксы (или в миксы не шло сигнала) |
| `0x16` | 1168B | 584 | недекодирован; те же пары, что 0x18, но на ~10 дБ тише (пре-фейдерные тапы?); статичные ~0 дБ на слотах 2,5,8,11,14 (шаг 3) — константы, на живые метры не похожи |
| `0x17` | 96B | 48 | **декодирован**: по уровню на вход |
| `0x18` | 480B | 240 | недекодирован; **главный кандидат**: 120 L/R-пар, значения ходят за программой; пары 75/76 всегда идентичны → стерео-линкованная шина; в громкие моменты горячие пары 24, 45, 75/76 |

Два захвата (18:59, 19:09–19:10) сделаны при обычной программе через много шин —
привязать пары к конкретным миксам по ним нельзя. Для привязки нужен изолированный
эксперимент (ниже). Диагностика теперь пишет и `hot:` — топ-6 самых горячих слотов
пакета (≥ −54 дБ), отсортированных по уровню; при изолированной подаче сигнала
верхний слот нужного пакета прямо называет шину.

### Анализ захвата 3 (19:22–19:23, изолированный эксперимент)

- **`0x07` (708)** — записи по **9 слотов** (18 байт), заголовок ~6 значений:
  708 = 6 + 78×9. У записей offset 2 — константа ~+0.1 (пик-латч?), offsets 4–8 —
  уровни группами {4,5,6} равны и {7,8} равны. Событие 19:22:46: запись 13
  (offsets 4–7) → +8.8 дБ. 78 записей похоже на «48 инпутов + 12 миксов +
  14 local outs + LR + 3 ST».
- **`0x18` (240 = 120 L/R-пар)** — у пар 24, 45, 75/76, 93 всплески во время
  событий; пары 69–71, 78, 108–110, 117–119 постоянно горячие (~−2…−8 дБ,
  медленно дышат — похоже на FX-возвраты / DCA / мониторные выходы с программой).
- **`0x16`** — зеркалит индексы `0x18` (на ~10 дБ тише), в хвосте (слоты 529+)
  статичные +17…+18 — параметр-данные, не уровни. Сентинел 0xFFFF (=«128.0 дБ»)
  на слотах 351/384/367/400 — данные, в hot теперь отфильтровываются.
- Событие 19:22:46 (пары 24/45/93 + записи 13 в 0x07) не удалось однозначно
  сопоставить с шагами эксперимента — нужен точный лог действий пользователя
  и/или сырые дампы пакетов.

### Сырые дампы (добавлено 2026-09-10)

При первом появлении недекодированного формата приложение сохраняет полный сырой
дейтаграмм в `<userData>/diagnostics/meter-packet-0x<id>-<len>B.bin` — один файл
на форму пакета за сессию. Файлы можно прислать для офлайн-разбора раскладки.

### Как собрать данные (нужен реальный пульт)

Цель: определить, в каком пакете и на каких слотах лежат уровни Mix 1–12 и Main LR.

**Подготовка (важно):**
- Мониторную сессию выключить (тумблер «Применять» — off): её шины
  подмешивают свои уровни и загрязняют картину.
- Лог теперь в «тихом режиме»: строки метров пишутся только когда слоты
  реально сдвинулись. Кнопка «Метка (M)» (или клавиша `M` на вкладке «Журнал»)
  ставит разделитель с временем — им размечаются шаги эксперимента.
- При первом появлении недекодированных форматов сырые дейтаграммы сохраняются
  в `<userData>/diagnostics/meter-packet-0x<id>-<len>B.bin` — файлы приложить
  к результату.

**Шаги (~10 с между метками):**
1. Подключиться, открыть «Журнал», нажать `M` (базовая линия).
2. Подать сигнал **только в Mix 1** → нажать `M`.
3. Убрать из Mix 1, подать **только в Mix 5** → `M`.
4. **Только в Mix 12** → `M`.
5. **Только в Main LR** → `M`.
6. Убрать сигнал совсем → `M`.

Способ подачи: канал с музыкой/тоном со всеми отправками, кроме целевой, вниз;
или сиг-генератор пульта, назначенный прямо на шину. Между шагами источник
не трогать. После — прислать лог (со метками) и файлы meter-packet-*.bin.
